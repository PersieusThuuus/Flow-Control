# FlowControl — Database Documentation

**ORM:** Prisma ^6.11.1 · **Engine:** SQLite (portable schema) ·
**Schema:** `prisma/schema.prisma` · **18 models**

## Design principles (stated in the schema header and enforced throughout)

1. **No SQLite-specific column types.** No `String[]` arrays, no `Decimal`.
   This keeps the schema portable: switching to PostgreSQL requires only
   changing the datasource `provider` and URL (§ "Migration path").
2. **Enums are strings validated at the boundary.** Prisma does not support
   native enums on SQLite, so role keys, statuses, actions and scopes are
   `String` columns validated by zod schemas in `src/server/*` (e.g.
   `src/app/api/approvals/[instanceId]/act/route.ts` restricts `action` to
   `APPROVE | REJECT | RETURN_FOR_CORRECTION | COMMENT`). When migrating to
   PostgreSQL, native enums can be introduced, but the string approach also
   keeps the audit chain's hash input stable.
3. **Money is `BigInt`, whole currency units.** JS numbers are safe integers
   ≤ 2^53, but currency arithmetic must be exact: amounts are `BigInt` end to
   end in services and serialized to `Number` only at the API boundary, with
   a hard cap of 999,999,999,999 enforced by `toBigIntAmount`
   (`src/server/api.ts`). BigInts never touch JSON directly (JSON has no
   BigInt); serializers convert explicitly.
4. **Append-only where history matters.** `AuditEvent`, `Approval`,
   `DocumentVersion`, `LoginAttempt` are never updated or deleted by the
   application; corrections create new rows.
5. **Snapshot denormalization for immutability.** Running workflows and
   historical decisions must survive later configuration changes — see
   `stagePath` on `WorkflowInstance` and the snapshot columns on `Approval`.

## Model reference

### Identity & organization

#### `Department`
- **Purpose:** organizational unit used for document ownership, department
  scoping of approval stages, and department-scoped visibility.
- **Key fields:** `code` (unique short code), `name`.
- **Relations:** `users User[]`, `documents Document[]`, `stages WorkflowStage[]`.
- **Constraints/indexes:** unique `code`.

#### `User`
- **Purpose:** application account with exactly one business role.
- **Key fields:** `email` (unique, lowercased on write), `passwordHash`
  (scrypt), `role` (RoleKey string — see `src/server/rbac.ts`),
  `departmentId?`, `isActive`, `failedLogins`, `lockedUntil` (lockout state),
  `lastLoginAt`.
- **Relations:** `department?`; `sessions`, `documentsCreated`
  ("DocumentCreator"), `versionsUploaded` ("VersionUploader"), `approvals`,
  `notifications`, `auditEvents`, `delegationsGiven`/`delegationsReceived`,
  `exceptionSubjects`. Department deletion sets `departmentId` to NULL
  (`onDelete: SetNull`) — users survive department removal.
- **Indexes:** `role`, `departmentId`, `isActive`.
- **Notes:** single role per user (design decision; affects `ROLE_PAIR` SoD
  enforcement — docs/LIMITATIONS.md).

#### `Session`
- **Purpose:** server-side session records backing cookie authentication.
- **Key fields:** `tokenHash` **unique** — HMAC-SHA256(token, SESSION_SECRET);
  raw 256-bit tokens are never stored. `expiresAt` (8h TTL), `revokedAt`
  (logout/deactivation/password reset), `ip`, `userAgent` (telemetry).
- **Relations:** `user` (cascade delete).
- **Indexes:** `userId`, `expiresAt`.

#### `LoginAttempt`
- **Purpose:** append-only log of every login attempt for audit dashboards
  and exports.
- **Key fields:** `email`, `success`, `reason`
  (`OK | INVALID_CREDENTIALS | ACCOUNT_LOCKED | ACCOUNT_DISABLED`), `ip`,
  `userAgent`.
- **Indexes:** `[email, createdAt]`, `[success, createdAt]` (24h failure
  aggregations in `stats.ts`).

### Document management

#### `DocumentCategory`
- **Purpose:** document taxonomy; drives workflow matching and the mandatory
  evidence control.
- **Key fields:** `code` (unique), `name`, `requiredEvidence` — JSON-encoded
  `string[]` of mandatory evidence item names (JSON column because SQLite
  has no arrays; parsed defensively in the engine).
- **Relations:** `documents`, `workflows`.

#### `Document`
- **Purpose:** the business request (purchase order, expense claim, …).
- **Key fields:** `reference` (unique, human-readable `DOC-YYYY-NNNNN`,
  generated by `nextDocumentReference`), `title`, `categoryId`,
  `departmentId`, `createdById`, `supplierName?`, `currency` (default
  `"MAD"`, validated as a 3-letter code at the API), `amount BigInt`,
  `evidenceProvided` (JSON `string[]`), `evidenceJustification?`,
  `status` (`DRAFT | IN_REVIEW | APPROVED | REJECTED | RETURNED | CANCELLED`),
  `currentVersion` (pointer to the latest `DocumentVersion`).
- **Relations:** `category`, `department`, `createdBy`, `versions`,
  `instances`, `exceptions`.
- **Indexes:** `status`, `categoryId`, `departmentId`, `createdById`,
  `createdAt`, `amount` (amount-window workflow matching and amount-range
  filters).

#### `DocumentVersion`
- **Purpose:** immutable version of the physical file — every modification
  appends a new version; nothing is ever overwritten.
- **Key fields:** `documentId` + `version` (**composite unique**
  `@@unique([documentId, version])`), `fileName` (original name, display
  only), `storageKey` (randomized UUID-based name inside `STORAGE_DIR`,
  never under `/public`), `mimeType`, `sizeBytes`, `sha256` (content hash —
  also pinned on every `Approval`), `note?`, `uploadedById`.
- **Relations:** `document` (cascade delete), `uploadedBy`, `approvals`
  (decisions reference the exact version reviewed).
- **Indexes:** `sha256` (duplicate detection possible), composite unique
  above.

### Workflow engine

#### `Workflow`
- **Purpose:** configurable approval routing for a document category and
  amount window.
- **Key fields:** `code` (unique, uppercase pattern enforced by the admin
  API), `categoryId`, `isActive`, `minAmount?`/`maxAmount?` (BigInt window).
- **Relations:** `category`, `stages`, `instances`.
- **Indexes:** `[categoryId, isActive]` (matching query).
- **Selection semantics:** active workflows of the category are filtered by
  amount window; if several match (misconfiguration), the most recently
  updated wins.

#### `WorkflowStage`
- **Purpose:** one approval stage inside a workflow.
- **Key fields:** `workflowId`, `sequence` (**stages sharing a sequence
  number form one parallel step**), `name`, `approverRole` (RoleKey —
  restricted to `APPROVER_ROLES` by the admin API; admins/auditors cannot be
  stage approvers), `departmentScope` (`ANY | DOCUMENT | FIXED`),
  `departmentId?` (required when `FIXED`), `minAmount?`/`maxAmount?` (stage
  applies only within its own amount range), `isRequired` (a step completes
  when all *required* stages approve), `slaHours?`.
- **Relations:** `workflow` (cascade delete), `department?` (SetNull).
- **Indexes:** `[workflowId, sequence]`.
- **Note:** `Approval` rows reference stages by plain `stageId` scalar +
  denormalized `stageName` snapshot, so workflow reconfiguration never
  rewrites approval history.

#### `WorkflowInstance`
- **Purpose:** one execution of a workflow for a document (one per
  submission, reused across review cycles).
- **Key fields:** `documentId`, `workflowId`, `status`
  (`IN_PROGRESS | APPROVED | REJECTED | RETURNED_FOR_CORRECTION | CANCELLED |
  SUSPENDED`), `stagePath` — **JSON snapshot of the resolved steps**
  (`[{sequence, stages:[{stageId, name, approverRole, departmentScope,
  departmentId, isRequired, slaHours}]}]`), immutable per cycle;
  `cycle` (increments on resubmission after a return), `currentStep` (index
  into `stagePath`, moved only by the CAS update in the engine),
  `amount` (snapshot of the document amount at submission — thresholds are
  checked against this, not against later document edits), `submittedAt`,
  `currentStepStartedAt` (SLA clock, reset on step change and on resume),
  `escalatedAt?`, `lastOverdueCheckAt?` (24h monitor re-check guard),
  `returnCount`, `suspendedById?`, `suspensionReason?`, `completedAt?`.
- **Relations:** `document` (cascade), `workflow`, `approvals`.
- **Indexes:** `status`, `documentId`, `submittedAt`.

#### `Approval`
- **Purpose:** one decision (or comment) by one user on one stage — the
  system of record for the approval history.
- **Key fields:** `instanceId`, `stageId` + `stageName` (**snapshot
  denormalization** — config changes never rewrite history), `cycle`,
  `stepIndex`, `action` (`APPROVE | REJECT | RETURN_FOR_CORRECTION |
  COMMENT`), `userId`, `userRole` / `userDepartmentId` (**snapshots** of the
  acting user's role/department at decision time), `delegatedFromId?`
  (delegation traceability), `documentVersionId` + `documentHash`
  (**decision pinned to the exact reviewed bytes**), `comment?`, `ip?`.
- **Relations:** `instance` (cascade), `user`, `documentVersion`.
- **Indexes:** `[instanceId, cycle, stepIndex]` (step-completion queries),
  `[userId, createdAt]` (history queries).
- **Integrity:** append-only; "edits" are new rows (e.g. a returned request
  re-approved in cycle 2).

#### `ApprovalDelegation`
- **Purpose:** time-boxed transfer of approval authority with full
  traceability.
- **Key fields:** `fromUserId`, `toUserId`, `reason`, `startAt`, `endAt`
  (max 30 days enforced by the API), `isActive`, `createdById`,
  `revokedAt?`.
- **Relations:** cascade delete from both users.
- **Indexes:** `[toUserId, isActive]` (engine eligibility lookup),
  `fromUserId`.
- **Enforcement:** the engine evaluates whether the *delegator* matches the
  stage; the delegate's Approval records `delegatedFromId`.

### Notifications & email

#### `Notification`
- **Purpose:** in-app notifications (always delivered, unlike email).
- **Key fields:** `userId`, `type` (`INFO | ACTION_REQUIRED | ALERT |
  SYSTEM`), `title`, `body?`, `link?` (e.g. `"document:<id>"`), `isRead`.
- **Indexes:** `[userId, isRead, createdAt]`.

#### `EmailLog`
- **Purpose:** honest record of email attempts — the system never claims an
  email was sent when it was not.
- **Key fields:** `toEmail`, `subject`, `status`
  (`SENT | SKIPPED_NO_SMTP | FAILED`), `detail`.
- **Behavior:** with no `SMTP_HOST`/`SMTP_PORT`, attempts are recorded as
  `SKIPPED_NO_SMTP`. No SMTP transport is wired in this delivery; wiring one
  (e.g. nodemailer) at `src/server/notify.ts queueEmail()` is the documented
  integration seam (docs/LIMITATIONS.md).

### Audit trail

#### `AuditEvent`
- **Purpose:** append-only, hash-chained audit trail — the system of record
  for "who did what, when, and on which entity".
- **Key fields:** `seq` (**explicit integer primary key**, monotonically
  assigned as `last.seq + 1` under the append mutex — a colliding insert
  fails and retries), `occurredAt`, `actorId?`/`actorRole?` (SetNull on user
  deletion — the event survives), `action` (39 action types,
  `src/server/audit.ts`), `entityType?`/`entityId?`, `details` (canonical
  JSON: recursively sorted keys, BigInt→string, Date→ISO), `ip?`, `prevHash`
  (`"GENESIS"` for the first row), `hash`
  (`SHA-256(seq|prevHash|occurredAt|actorId|action|entityType|entityId|details)`).
- **Indexes:** `action`, `[entityType, entityId]`, `occurredAt`.
- **Integrity:** no API updates or deletes audit rows; the verification
  endpoint recomputes the chain and reports the first broken `seq`.
  Limitations (DBA with write access can recompute the chain) are documented
  in docs/SECURITY.md §4.

### Internal control configuration & exceptions

#### `SoDRule`
- **Purpose:** segregation-of-duties rule configuration.
- **Key fields:** `code` (unique), `name`, `ruleType`
  (`SELF_APPROVAL` — hard block; `MULTI_STAGE_SAME_USER` — hard block;
  `ROLE_PAIR` — configurable, alert-oriented), `roleA?`/`roleB?` (for
  `ROLE_PAIR`), `severity`, `isActive`.
- **Enforcement points:** `src/server/engine.ts` (self-approval and
  multi-stage checks consult the active rules; a disabled rule disables the
  block).

#### `ApprovalRule`
- **Purpose:** per-role approval threshold (financial limit).
- **Key fields:** `role` (**unique** RoleKey), `maxAmount BigInt?`
  (`null` = unlimited, `0` = cannot approve at all), `currency`.
- **Least privilege:** a role with **no row** is treated as limit 0 — it
  cannot approve (`src/server/engine.ts`).

#### `ControlException`
- **Purpose:** recorded internal-control events — both blocked violations
  and detected patterns.
- **Key fields:** `type`
  (`SOD_SELF_APPROVAL | SOD_ROLE_PAIR | SOD_MULTI_STAGE | THRESHOLD_BREACH |
  OVERDUE_STAGE | REPEATED_RETURN | REPEATED_REJECTION | FAST_TRACK_SEQUENCE |
  MISSING_EVIDENCE | UNAUTHORIZED_ACCESS`), `severity`, `message`,
  `documentId?` (SetNull), `instanceId?`, `userId?` (subject, SetNull),
  `details` (JSON), `detectedAt`, `resolvedAt?`, `resolution?`.
- **Indexes:** `[type, detectedAt]`, `resolvedAt`, `documentId`.
- **Lifecycle:** resolution is additive (note + timestamp via
  SUPER_ADMIN-only endpoint); the original record is never rewritten.

## JSON-snapshot design decisions (summary)

| Column | Why JSON snapshot |
|---|---|
| `WorkflowInstance.stagePath` | Freezes the resolved steps for the cycle. Later workflow/stage edits (renames, resequencing, deletion) cannot alter an in-flight or historical instance. |
| `Approval.stageId` + `stageName` (+ role/department snapshots) | Decisions must outlive configuration changes; the denormalized name is what auditors read. |
| `DocumentCategory.requiredEvidence`, `Document.evidenceProvided` | Variable-length string lists without a join table; parsed defensively (`try/catch` JSON.parse) everywhere. |
| `ControlException.details` | Flexible, typed-at-runtime payloads per exception type. |

## Integrity notes

- **Append-only tables:** `AuditEvent`, `Approval`, `DocumentVersion`,
  `LoginAttempt`, `EmailLog` have no update/delete paths in the application.
- **Transactional writes:** every multi-row business mutation (submit, act,
  cancel, suspend, user admin, delegation, document creation) runs in a
  `db.$transaction`, so state + exception + audit + notification commit
  atomically — including *blocked* violations (evidence is committed before
  the API error is returned).
- **Cascade policy:** dependent operational rows (sessions, approvals,
  instances, versions, notifications, delegations) cascade-delete with their
  parents; referential/audit rows (audit actor, exception document/subject,
  department references) use `SetNull` so records survive user/department
  deletion. In practice demo data never deletes users.
- **Money:** `BigInt` everywhere in the DB and services; `Number` conversion
  only at the DTO boundary with a ≤ 999,999,999,999 guard.

## Migration path: SQLite to PostgreSQL

The schema was written for this path (see the header comment in
`prisma/schema.prisma`):

1. Change the datasource:
   ```prisma
   datasource db {
     provider = "postgresql"
     url      = env("DATABASE_URL")
   }
   ```
2. Set `DATABASE_URL` to the PostgreSQL connection string.
3. `bun run db:generate` (regenerate the client), then adopt migrations:
   `prisma migrate dev` instead of the dev-only `db:push` script.
4. Transfer data (demo scale: export/import scripts; production: ETL).
5. No model changes are required — no SQLite-specific types are used; string
   "enums" remain valid (or introduce native enums consciously, knowing the
   audit hash serialization is unaffected since it hashes strings either way).
6. Revisit operational assumptions: multi-instance audit locking and DB-level
   permissions (docs/ARCHITECTURE.md §12, docs/SECURITY.md §5).

A commented `postgres` service profile exists in `docker-compose.yml` for
this purpose.
